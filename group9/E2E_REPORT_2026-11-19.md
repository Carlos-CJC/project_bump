## 3. 第一轮：问题复现（修复前固件）

### 3.1 成功路径

- 20:17:52 挂件 B 判定与挂件 A 相遇（2 次采样，停留 32s），队列 `q=1`。
- 20:18:05 B 进入上传窗口：Wi-Fi 成功、MQTT 连接成功、`tx ok`，20:18:17 桥接入库。
- 20:18:17 网页 bob 可见 1 条「挂件 MQTT 直传」单方记录。

### 3.2 失败路径

挂件 A 每次进入上传窗口，都在 Wi-Fi 成功后 8–9 秒内整机复位，内存队列里的相遇随之丢失：

| 时间 | 事件 |
|---|---|
| 20:20:15 | A 开始上传（`queued=1`） |
| 20:20:21 | `wifi ok attempt=1 ip=172.20.10.12` |
| 20:20:32 | 全新 `[boot]`，boot ID 变为 `78d5e9b5`，short 变为 `abc6a7df0c88`，事件丢失 |
| 20:23:50 | 重试，Wi-Fi 成功 |
| 20:23:59 | 再次复位，事件丢失 |
| 20:25:52 | 换成 B 上传，Wi-Fi 成功 |
| 20:26:00 | `mqtt connected` |
| 20:26:02 | B 也复位，事件丢失 |

结果：网页 alice 没有任何记录；bob 有 2 条记录，对端均显示「身份待匹配」（A 的 short 从未成功上传注册）。这正是「总是只有一块板子收到」的直接原因。

### 3.3 根因

1. RP2040 的 mbed `Watchdog::get_max_timeout()` 上限约为 **8388ms**（Pico SDK 的看门狗常量同样标注约 8.3s）。
2. 固件请求 `BUMP_WDT_TIMEOUT_MS = 16000`，被 `watchdogStart()` 静默截断到约 8.3s，但串口日志仍打印请求值 `timeout=16000ms`，具有误导性。
3. `mqtt.setConnectionTimeout(BUMP_MQTT_TIMEOUT_MS = 10000)` 允许 `mqtt.connect()` 单次阻塞最多 10 秒，阻塞期间无法喂狗。
4. TLS 握手在 NINA 硬复位后偶尔需要 6–10 秒；一旦超过约 8.3 秒，看门狗就在「上传中」复位整机，RAM 事件队列全部丢失，形成「偶发、只丢一个方向」的现象。

### 3.4 修复

提交 `752d71c fix(mqtt): 连接超时限制在 RP2040 看门狗上限内，避免上传中复位丢事件`

- `BUMP_MQTT_TIMEOUT_MS`：10000 → 5000，使单次阻塞远低于看门狗实际上限；仍保留两次连接尝试与失败退避。
- 注释补充看门狗实际被截断的事实，避免再次踩坑。

## 5. 结论

通过：

- BLE 互补时分發現窗口正常工作，两块板能互相发现。
- 单方相遇即可上报、入库、展示，语义符合要求。
- 公网 MQTT（TLS/QoS1）+ 服务端桥接落库链路正常，无串口中转。
- 修复后在 Wi-Fi 多次失败、热点关闭又恢复的情况下，内存队列完整保留，恢复后一次上传成功且不再复位。
- 前端两条记录的时间、信号、采样数与串口日志一致。

本次修复解决的核心问题：

- 上传窗口内的整机复位已消除；「只有一块板子收到」不再由上传中断丢队列导致。

## 6. 遗留观察与建议

1. **看门狗日志应打印生效值**：目前仍打印请求的 16000ms，实际约 8388ms。建议在 `watchdogStart()` 中返回/记录 `get_max_timeout()` 截断后的值，避免误判。
2. **身份解析依赖对方上传**：服务端只有在收到某设备 encounters 上传后才会登记其 short；对方尚未上传时显示「身份待匹配」。这属于既有规则，可考虑在 UI 上补充 short 摘要便于排查。
3. **公网主题混入第三方设备**：本轮桥接日志出现未登记设备 `bump-0644376c5691` 的告警；B 还观察到 `753e79e580f8`、`8103d58b22ae`、`da9acd554223`、`c295084cabc2` 等陌生 short，说明附近有其他组使用同一协议在同一公网主题上报。最终提交建议改用私有 broker 或按设备身份隔离主题。
4. **iPhone 热点会自动关闭**：无设备连接一段时间后热点关闭，导致 `status=4`。固件当前以「多次重试 + 指数退避 + 队列保留」应对，本轮验证不会丢数据；演示前建议保持热点开启。
5. **mutual 匹配窗口**：服务端要求反向观察在 15 分钟内才能标记双方记录；本轮两条记录未满足，但按需求单方记录已足够。
