# 双板可靠性验证

run_dual_reliability.py 通过运行中的 board_session 命令队列驱动两枚挂件。两块板需运行指定版本，已配置本机 MQTT，退出暂停，且已有待发记录已收到回执。运行期间用同一个 board_session 独占两个 USB 串口。

在 Bump 项目根目录执行，按实际会话更换目录，并使用新建的报告文件名。

~~~powershell
$run = '.\2026-11-18_双板联调'
python -B "$run\firmware\verification\run_dual_reliability.py" --expect-fw 0.5.5-dual --session "$run\hardware\logs\当前会话" --db "$run\private\live\live.sqlite3" --output "$run\firmware\verification\新一轮结果.jsonl" --rounds 20
~~~

每轮向两板下发 discover，确认两侧开启各自的 60 秒诊断发现窗。默认开窗偏差最多 2 秒。串口命令只负责开窗，两边需通过真实 BLE 接收对方广播。报告包含发出命令及开窗时间、初次观测预览、合格事件的采样数和时长、每事件方向及 ID、broker PUBACK、应用回执和对应入库行。

每个方向须有一条符合门槛的独立观测，且通过直连 MQTT 入库并收到匹配应用回执。旧 ID、重复使用的 ID、串口中转入库和发生复位的轮次均不计成功。脚本等候已有队列出清，下一轮才开始。两侧结束后默认再等 65 秒入库和回执，可用 --ack-timeout 调整。前两轮均无完整双向时结束，并报告实际轮数。未跑满轮数或发生失败时返回 1。

请明确传入板上安装的版本号。诊断开窗使用 `serial_diagnostic` 标签。使用 `--source hardware --rounds 1` 时，验证工具等两块板各自的真实 IMU 触发及后续事件。需要模拟两人开窗的先后时差时，可使用 `--b-leads-by 12.247` 在 B 之后打开 A；报告记录实际开窗差，空口采样仍来自真实挂件。`--restore-network-from` 可在轮次之间根据原临时热点和原本机接收服务重新下发网络配置，轮内复位仍计失败。离线脚本 `test_dual_reliability.py` 用虚构串口记录及临时数据库核对上述验收逻辑。
