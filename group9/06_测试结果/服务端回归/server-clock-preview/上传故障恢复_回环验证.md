# 上传失败及确认未达的恢复验证

2026-11-19，使用本目录的 live_server.py 正常启动入口，以及与既有 smoke_test.py 相同的客户端、隔离初始化与服务就绪检查，完成一次三阶段测试。发布者是模拟挂件 A，消息为同一批次的两条有效 BLE 格式观察，三次使用相同报文内容。MQTT 和 HTTP 仅绑定 127.0.0.1 的临时端口，SQL 操作仅作用于当次新建的临时 SQLite 库。服务退出后临时目录自动清理。

| 同一批次的发送次序 | MQTT 发布方 | 接收端与 SQLite | 设备端应用回执 |
|---|---|---|---|
| 首发，在第二个 INSERT 前拒写 | 收到 QoS 1 PUBACK | 触发条件要求本事务里已经看见第一条，由 SQLite 抛出指定故障。另一连接读到观察表 0 行；服务记录存储失败，应用 ACK 排队 0 条。 | 正在订阅，收到 0 条。 |
| 移除故障并第一次重发 | 收到 QoS 1 PUBACK | 两个事件各 1 行；服务逐条记录 2 条 stored 回执已排队。 | 唯一客户端先取消回执主题订阅，并收到 UNSUBACK。本轮收到 0 条。 |
| 恢复订阅并第二次重发 | 收到 QoS 1 PUBACK | 再次读取，两事件仍各 1 行。 | 收到 SUBACK 后先确认没有遗留回执，再发送原批次。两事件各收到 1 条对应的 duplicate 应用回执。 |

故障注入通过临时库上的 SQLite 触发器完成，按事件编号和本事务可见的第一条记录触发。第一次成功提交后的回执缺失由订阅中断产生。测试复用了实际解析、事务、消息监听和应用确认通路；它提供服务器侧的恢复证据，未测量实物固件自动重发间隔或清队行为。
